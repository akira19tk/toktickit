# Lab 2 Sprint Engineering Specification — TokTickIT Requester Ticketing MVP

## 1. Sprint Goal

Deliver a working, testable vertical slice of the Requester-facing TokTickIT experience: a
Requester (simulated via a temporary Development Requester selector) can create an IT
support ticket with attachments, find it again in a searchable/filterable/sortable My
Tickets list, open its read-only Detail screen, and manage its attachments — all built on
the Zen Green UI system and backed by real PostgreSQL data through Prisma and an Express
REST API.

## 2. Stakeholder Request Interpretation

The IT department wants a professional, responsive ticket-submission experience before any
real login exists. Concretely: a Requester must be able to describe a problem (category,
related system, requested priority, summary, description), attach evidence, and get back an
official Ticket Number. They must later find that ticket among their own tickets only —
never another Requester's — search/filter/sort/page through the list, inspect a Ticket's
current state, and add or remove attachments under fixed rules. Because authentication does
not exist yet, a Development Requester Selection screen stands in as a testing mechanism,
explicitly not real security, and will be replaced by Lab 3 authentication.

## 3. Scope

### Included
- Development Requester Selection screen, context, and switching
- Create Ticket (form, validation, attachment upload, Ticket Number generation)
- My Tickets (search, filter, sort, pagination, ownership-scoped list)
- Requester Ticket Detail (read-only header + attachment list)
- Attachment lifecycle: add, download, soft-remove
- Zen Green UI foundation: reusable form/list/badge/validation/loading/empty/error styles
- Automated tests: unit, API, UI component, responsive/visual, E2E
- GitHub Issues, feature branches, `lab2-staging` integration, peer review

### Excluded
- Authentication: login, logout, passwords, hashing, sessions, tokens, real authorization
- IT Staff dashboard, queue, ticket assignment, IT Priority, ticket ownership transfer
- Public Comments, Internal Notes, Actions Taken
- Any ticket status transition beyond the initial `New` status (resolve/close/reopen/cancel)
- Administrator functions: user management, role management, reference-data management

## 4. Functional Requirements

- **FR-01** The system shall allow a Requester to create a new Ticket by submitting
  Category, Related System, Summary, Description, Requested Priority, and optional
  Attachments.
- **FR-02** The system shall generate a unique Ticket Number and Ticket Date on successful
  Ticket creation and return them to the client.
- **FR-03** The system shall allow a user to select and switch their Development Requester
  identity via a dedicated selection screen before accessing Ticket screens.
- **FR-04** The system shall list only active Development Requesters in the selection
  screen.
- **FR-05** The system shall list on My Tickets only the Tickets owned by the currently
  selected Requester.
- **FR-06** The system shall allow the Requester to search My Tickets by Ticket Number or
  Summary text.
- **FR-07** The system shall allow the Requester to filter My Tickets by Category, Requested
  Priority, and Current Status.
- **FR-08** The system shall allow the Requester to sort My Tickets by at least Created Date
  and Ticket Number, ascending or descending.
- **FR-09** The system shall paginate My Tickets results and expose pagination metadata
  (current page, total pages, total count, page size).
- **FR-10** The system shall allow the Requester to open a Ticket Detail screen for a Ticket
  they own.
- **FR-11** The system shall prevent a Requester from retrieving, viewing, or modifying a
  Ticket or Attachment they do not own, at the API layer, regardless of what the client
  requests.
- **FR-12** The system shall allow the Requester to add a permitted Attachment to an
  existing owned Ticket.
- **FR-13** The system shall allow the Requester to download an active (non-removed)
  Attachment they own.
- **FR-14** The system shall allow the Requester to soft-remove an owned Attachment by
  providing a removal reason.
- **FR-15** The system shall reject Attachments that exceed the allowed type/size limits or
  that would exceed the maximum active-attachment count per Ticket.
- **FR-16** The system shall display loading, success, empty, no-results, and error states
  on the Development Requester Selection, Create Ticket, My Tickets, and Ticket Detail
  screens.
- **FR-17** The system shall retain all entered Create Ticket form values when submission
  fails, so the Requester does not need to re-enter data.
- **FR-18** The system shall validate all required fields on both frontend and backend and
  return field-level error messages on failure.

## 5. Business Rules

- **BR-01** The official Ticket Number is generated by the backend and must be unique.
- **BR-02** A new Ticket begins with Current Status `New`.
- **BR-03** Lab 2 uses a Development Requester selector instead of login. The selected
  identity is for testing only and is not authentication.
- **BR-04** Only active Development Requesters appear in the selector; inactive Requesters
  cannot be selected or set as the active context.
- **BR-05** The selected Development Requester persists in client-side state until changed
  or the session ends. It grants no server-side trust beyond a testing convenience and is
  re-validated by the backend on every request.
- **BR-06** Every Ticket must be associated with exactly one Requester (`requesterId`) at
  creation time; `requesterId` is never null.
- **BR-07** A Requester may view, list, or modify Attachments only on Tickets where
  `ticket.requesterId` matches the currently selected Requester context.
- **BR-08** Ticket Date is a system-generated server timestamp at creation time and is not
  editable by the Requester.
- **BR-09** Requested Priority is required and must be one of `LOW`, `MEDIUM`, `HIGH`; no
  value is pre-selected — the Requester must make an explicit choice.
- **BR-10** Category and Related System must reference existing, active seeded records;
  invalid or inactive IDs are rejected with `400`.
- **BR-11** Ticket Summary is required, trimmed of leading/trailing whitespace, and must be
  5–120 characters. Description is required, trimmed, and must be 10–2000 characters.
- **BR-12** The frontend must disable/busy the Submit button while a create request is in
  flight, preventing a second Ticket from being created by a duplicate click.
- **BR-13** If Ticket creation fails (validation or server error), all previously entered
  field values must be retained in the form.
- **BR-14** Allowed attachment types are JPG/JPEG, PNG, WEBP, and PDF; maximum size is 5 MB
  per file; maximum active attachments per Ticket is five.
- **BR-15** If Ticket creation succeeds but one or more accompanying Attachment uploads
  fail, the Ticket is still saved; the Requester is shown which attachments failed and why,
  with the option to retry adding them from Ticket Detail.
- **BR-16** A soft-removed Attachment remains stored with a `removedAt` timestamp and a
  removal reason, is excluded from the active-attachment count, and cannot be downloaded or
  previewed.
- **BR-17** Only the owning Requester (matching `Ticket.requesterId` under the current
  context) may add or soft-remove Attachments on a Ticket.
- **BR-18** Removing an Attachment requires the Requester to provide a removal reason of at
  least 3 characters before the removal is confirmed.
- **BR-19** An inactive Development Requester must not appear in the selector; if a
  previously selected Requester becomes inactive, the next request under that context is
  rejected and the user is returned to the Selection screen.
- **BR-20** My Tickets search is a case-insensitive substring match against Ticket Number
  and Summary.
- **BR-21** Filtering by Category, Requested Priority, and Current Status uses exact match;
  multiple active filters combine with AND logic.
- **BR-22** The default sort order is Created Date descending (most recent first) unless the
  Requester chooses another sort field or direction.
- **BR-23** Default page size is 10; maximum permitted page size is 50. Invalid or
  out-of-range `page`/`pageSize` values fall back to defaults rather than producing an error.
- **BR-24** If the current Requester owns zero Tickets at all, My Tickets shows an Empty
  state with a Create Ticket call-to-action. If Tickets exist but the current search/filter
  combination matches none, a distinct No-Results state is shown with a Clear Filters
  action.
- **BR-25** Ticket Detail and Attachment endpoints re-validate ownership on the backend on
  every request, independent of what the frontend has already rendered.
- **BR-26** All Lab 2 ownership and identity checks rely solely on the selected Development
  Requester context. In Lab 3, `requesterId` resolution must be replaced by the
  authenticated user's identity, and the Development Requester Selection mechanism must be
  removed or disabled.
- **BR-27** A Ticket's Current Status remains `New` for the entire scope of Lab 2; no status
  transition logic is implemented until a later lab.

## 6. UI Specification Summary

All screens follow the Zen Green theme (see `ui-spec.md` for full token definitions):
primary green `#006B3C`, secondary green `#0B7A46`, pale green `#EAF6EF`, quiet background
`#F5F7F6`, white surfaces with restrained shadow, dark charcoal-green text.

- **Application shell**: TokTickIT title, My Tickets / Create Ticket navigation, current
  Development Requester name with a Change Requester action, responsive mobile nav.
- **Development Requester Selection**: dropdown of active Requesters, loading/empty/failure
  states, keyboard-accessible, Continue button gated on a selection being made.
- **Create Ticket**: system-generated fields visually distinct (read-only styling) from
  editable fields; required-field asterisks; validation messages directly under each field;
  busy/disabled Submit button while in flight; success state showing the generated Ticket
  Number.
- **My Tickets**: search box, Category/Priority/Status filters, sortable columns, pagination
  controls, Create Ticket action, loading/empty/no-results/failure states; desktop table
  collapses to a card layout on mobile.
- **Ticket Detail**: read-only header block clearly separated from an Attachments section
  (add / download / soft-remove with reason), loading/failure states.
- **Responsive breakpoints**: desktop ≥992px multi-column; tablet 768–991px two-column;
  mobile <768px single-column stacked fields, touch-friendly buttons, no horizontal scroll.

## 7. Data Changes

New/updated Prisma models for Lab 2 (illustrative — final field list lives in
`schema.prisma`):

```prisma
model DevRequester {
  id        Int      @id @default(autoincrement())
  name      String
  email     String   @unique
  isActive  Boolean  @default(true)
  createdAt DateTime @default(now())
  tickets   Ticket[]
}

model RelatedSystem {
  id        Int      @id @default(autoincrement())
  name      String   @unique
  isActive  Boolean  @default(true)
  tickets   Ticket[]
}

model Ticket {
  id                Int             @id @default(autoincrement())
  ticketNumber      String          @unique
  requesterId       Int
  requester         DevRequester    @relation(fields: [requesterId], references: [id])
  categoryId        Int
  category          Category        @relation(fields: [categoryId], references: [id])
  relatedSystemId   Int
  relatedSystem     RelatedSystem   @relation(fields: [relatedSystemId], references: [id])
  summary           String
  description       String
  requestedPriority Priority
  currentStatus     TicketStatus    @default(NEW)
  createdAt         DateTime        @default(now())
  updatedAt         DateTime        @updatedAt
  attachments       Attachment[]

  @@index([requesterId])
  @@index([createdAt])
}

model Attachment {
  id             Int       @id @default(autoincrement())
  ticketId       Int
  ticket         Ticket    @relation(fields: [ticketId], references: [id])
  fileName       String
  storedFileName String
  mimeType       String
  sizeBytes      Int
  uploadedAt     DateTime  @default(now())
  removedAt      DateTime?
  removalReason  String?

  @@index([ticketId])
}

enum Priority     { LOW MEDIUM HIGH }
enum TicketStatus { NEW }
```

- `ticketNumber` is unique and generated server-side (e.g. `TKT-YYYY-NNNNNN`).
- `requesterId` is a required foreign key — enforces BR-06.
- `Attachment.removedAt` / `removalReason` implement soft removal (BR-16).
- Indexes on `requesterId` and `createdAt` support ownership filtering and default sorting.
- Migration adds `DevRequester`, `RelatedSystem`, `Ticket`, `Attachment` and extends the seed
  script (idempotent via `upsert`) with 4+ active Requesters, 1+ inactive Requester, and 6+
  Related Systems.

## 8. API Contract

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/dev-requesters` | List active Development Requesters |
| GET | `/api/categories` | List active Categories (from Lab 1) |
| GET | `/api/related-systems` | List active Related Systems |
| POST | `/api/tickets` | Create a Ticket (+ optional attachment files) |
| GET | `/api/tickets` | List the current Requester's Tickets (search/filter/sort/page) |
| GET | `/api/tickets/:id` | Retrieve one owned Ticket |
| POST | `/api/tickets/:id/attachments` | Upload an Attachment to an owned Ticket |
| GET | `/api/tickets/:id/attachments/:attachmentId/download` | Download an active Attachment |
| DELETE | `/api/tickets/:id/attachments/:attachmentId` | Soft-remove an owned Attachment |

Notes:
- The current Requester context is sent as a header/param (e.g. `x-requester-id`) on every
  request; the backend treats it as the ownership key for Lab 2 only (BR-26).
- `GET /api/tickets` query params: `search`, `category`, `priority`, `status`, `sortBy`,
  `sortDir`, `page`, `pageSize`. Invalid `page`/`pageSize` fall back to defaults (BR-23).
- Ownership failures (Ticket/Attachment belonging to a different Requester) return `404`,
  not `403`, so as not to reveal existence to a non-owner (see Section 11).
- `POST /api/tickets` response: `201` with the created Ticket (including `ticketNumber`) on
  success; `400` with field-level errors on validation failure.
- `POST /api/tickets/:id/attachments` response: `201` on success; `400` for
  unsupported-type/oversized/limit-exceeded; `404` if the Ticket is not owned by the current
  Requester.
- `DELETE .../attachments/:attachmentId` requires a JSON body `{ "reason": string }` (≥3
  chars); returns `200` with the updated (removed) Attachment metadata.

### Example: create ticket (partial)

```json
POST /api/tickets
{
  "categoryId": 2,
  "relatedSystemId": 5,
  "summary": "Laptop battery drains quickly",
  "description": "Battery drains fast even when idle, started after Windows update.",
  "requestedPriority": "MEDIUM"
}
```

```json
201 Created
{
  "id": 41,
  "ticketNumber": "TKT-2026-000041",
  "currentStatus": "NEW",
  "createdAt": "2026-09-06T10:15:00Z",
  "requesterId": 3
}
```

## 10. Definition of Done

**Product completion**
- All Functional Requirements (FR-01–FR-18) are implemented and demonstrable.
- Every Acceptance Criterion (AC-01–AC-32) has at least one passing, traceable automated
  test, recorded in `tests.md`.
- No required test is skipped, disabled, or commented out in the final `main` branch.
- Backend enforces ownership independently of the frontend (BR-07, BR-25).
- Create Ticket, My Tickets, and Ticket Detail conform to `ui-spec.md`, including
  responsive behavior at desktop/tablet/mobile.
- Success, validation-failure, server-failure, empty, and no-results states are all
  implemented and visibly distinct.
- README setup/run/test instructions are current for Lab 2.

**Course delivery**
- Each Issue implemented on its own feature branch, merged into `lab2-staging` via a
  peer-reviewed Pull Request.
- One release Pull Request merges `lab2-staging` into `main` after all Issues are Done.
- `reviewer.md` records reviewer identity, PR links, comments given/received, and
  responses, in both directions.

- Required documents (`specification.md`, `tests.md`, `ui-spec.md`, `api-spec.md`) exist,
  are internally consistent, and predate the implementation PRs.

## 11. Assumptions and Decisions

- **Ownership-failure status code**: `404 Not Found` is used (not `403 Forbidden`) for
  Tickets/Attachments owned by a different Requester, to avoid confirming that a resource
  exists for a non-owner — a defensible security-by-obscurity default given Lab 2 has no
  real authentication yet.
- **Summary/Description length limits**: 5–120 and 10–2000 characters respectively, chosen
  to be generous enough for real descriptions while catching obviously empty or accidental
  input; enforced identically on frontend and backend.
- **Ticket Number format**: `TKT-YYYY-NNNNNN` (year + zero-padded sequence), generated
  inside the same database transaction as Ticket creation to guarantee uniqueness.
- **Duplicate-submission prevention** is handled at the UI level only (disabled/busy button)
  for Lab 2; server-side idempotency keys are treated as an enhancement out of scope.
- **Requester context transport**: passed as a request header (`x-requester-id`) rather than
  a cookie/session, consistent with BR-03's explicit statement that this is not real
  authentication.
- **Filter combination logic**: AND (not OR) across Category/Priority/Status, matching how
  most users expect list filters to narrow results.
- **Page size bounds**: default 10 / max 50, balancing readable list length against
  reasonable payload size; out-of-range values silently clamp rather than erroring, to keep
  the UI resilient to manual URL edits.
